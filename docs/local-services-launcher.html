Local Services Launcher

Codex start automatically suppresses browser opening. Direct launcher/script calls retain their opening behavior. The primary operator entry point is node enterprise/operator.mjs start/status/stop/publisher, which delegates to this launcher. Direct launch.mjs/start-workspace.cmd usage below remains compatible. Start Research Workspace through one repeatable command. Research Publisher remains independent and opens directly without services.

Codex setup panel

Run node enterprise/operator.mjs setup and have Codex open the printed local URL in its built-in browser. It provides Check again, Start services and Stop owned services. These reuse this launcher and its ownership rules. No separate admin dashboard or data workflow is added. Configuration and prerequisites still follow the setup steps below. The Node process must remain running; closing the page does not stop services. See OPERATOR.md for scope and verification limits.

Everyday use

On Windows, double-click start-workspace.cmd from the prepared checkout/reference package. With configuration already in place, it checks the database, reuses running services, starts missing supported services, waits for readiness and opens a short API instruction page in the default browser. Browser administration is retired. The terminal command returns while a small local supervisor keeps owned services running. Closing Codex or its chat is not a shutdown command.

From the project root, the same actions are available to an operator or Codex:

node enterprise/launch.mjs start
node enterprise/launch.mjs status
node enterprise/launch.mjs stop
node enterprise/launch.mjs publisher

Start is the default action. start-workspace.cmd also accepts start, status, stop or publisher. Add --no-open to avoid opening a browser. Publisher only opens the prepared publisher/index.html; it does not start Node services or Neo4j. Without Node, open that file directly.

Codex can invoke the same script with the existing configuration. Startup does not require an LLM or Codex. For automation, use the Node command and its exit code; the Windows wrapper pauses on errors unless WORKSPACE_LAUNCHER_NO_PAUSE=1. A browser-open failure reports the ready URL rather than stopping the services.

One-time setup

Requirements: Node 24 or later; either Docker with Compose and the existing Neo4j image, or an independently running Neo4j instance. The script does not install software, pull images, configure a new password, create user credentials, import fixtures or seed data.

  1. Complete the database/access setup in ENTERPRISE_REFERENCE.md. Keep the existing database password for an existing installation. If access.json already exists, do not regenerate or overwrite it. For a fresh demonstration installation only, node enterprise/manage.mjs init creates ignored credentials and refuses overwrites. Seeding a fictional example is a separate optional command.
  2. Copy enterprise/launcher.example.json to .local/enterprise/launcher.json. Set database_mode to docker or external. All relative configuration paths resolve from the project root, not the terminal's current directory.
  3. Set the existing NEO4J_PASSWORD in the local environment, or place it in the configured ignored password_file. The latter is a JSON object with a password field. Keep that file outside exports and chat. The environment password takes precedence. Do not paste a real password into documentation or source control.
  4. Confirm .local/enterprise/access.json contains the existing authorized credential hashes. The launcher does not display plaintext Workspace credentials; obtain your operator credential from the previously provisioned local source.
  5. Run operator start, then status. Use the provisioned local connection file with inspect/import/export; the browser administration page is retired. Stop when finished.

The supplied example uses Docker and http://127.0.0.1:7474. Compose reuses its configured named volume and existing container. Docker mode uses the repository's fixed enterprise/compose.yaml, starts only neo4j with --no-build --pull never, and requires its image to be available already. Use the documented manual setup once if Docker or the image is missing. Port 7474 must be free or serving the intended Neo4j instance.

For an existing/portable installation, choose external mode and set neo4j_url to its loopback URL, for example http://127.0.0.1:17474. Start that installation by its existing mechanism first. This launcher does not start or stop portable Neo4j or a remote database. Automatic database startup in this milestone supports the supplied Docker Compose setup only.

Supported fields are database_mode, neo4j_url, password_file, access_file, port and startup_timeout_seconds (5–300, default 90). Environment overrides: WORKSPACE_LAUNCHER_CONFIG selects another config file; NEO4J_URL, NEO4J_PASSWORD, NEO4J_DATABASE, REFERENCE_PORT and REFERENCE_ACCESS_FILE override the matching settings. The local launcher accepts only plain HTTP loopback database URLs. Hosted/remote infrastructure uses its own deployment procedure.

Ownership and repeatability

  • Start verifies the configured database using an authenticated read-only readiness query. A running container that fails readiness is reported; it is not silently restarted or reset. Workspace startup retains the backend's idempotent database constraints; it never imports or seeds records.
  • A healthy existing Workspace is reused. An occupied port belonging to another service is reported; no process is killed to free it.
  • Repeated Start connects to the existing supervisor and reuses it. Status checks database and Workspace responsiveness, rather than assuming a saved ready flag means healthy.
  • Stop closes only the Workspace server object created by the live supervisor. It stops a Docker container only when that supervisor started it and its exact container ID/start timestamp still match. Reused and external services are left running. It never runs Compose down or removes volumes.
  • A failed Workspace start rolls back services the launcher positively owns. If Docker startup fails before ownership can be confirmed, inspect Docker state manually; the launcher does not guess which process to stop.

The supervisor uses a small authenticated loopback control endpoint with only status and stop actions. Its random control token/state are stored in ignored .local/enterprise/launcher-state.json, with restrictive file mode requested. Review Windows folder permissions when provisioning the machine. No arbitrary command or browser control panel is exposed; browser-origin requests are rejected. Do not share the state file or print its token.

After a crash, a later command removes only matching state whose recorded process no longer exists. It never kills a process from a saved PID. If that PID is still alive but control is unreachable, the script refuses to guess; inspect the current process and configuration before manually clearing stale state. Services left running after a supervisor crash are treated as external on the next launch, not silently adopted for shutdown. Do not delete a live state file.

Troubleshooting

ResultAction
Password not configured / access configuration missingComplete the one-time ignored configuration. Never put secrets in chat.
Docker unavailable or image missingStart/install Docker and prepare the pinned image through the manual setup, or use external mode with an existing database.
External Neo4j not readyStart the existing instance; verify its URL, password and port.
Neo4j running but not readyInspect the existing service/password; the launcher will not reset it.
Workspace port occupiedUse the intended running Workspace or choose another configured port.
Readiness timeoutRun status and inspect local service configuration. No dataset was reset.
Launcher control unavailableRetry status shortly. Do not stop processes by a saved PID or remove live state.
Browser could not openOpen the printed loopback URL manually; the services remain available.

Command output from Docker and raw exception details are suppressed so credentials cannot leak through an error. No data migration, deployment to another machine or production SSO is added by this launcher.

Verification and human acceptance

Automated tests cover reuse, start/stop ownership and order, rollback, port conflicts, readiness timeout, exact Docker ownership, credential/config handling, private control routing, and a real supervisor/CLI round trip against a simulated database endpoint. Real Docker/image startup and default-browser opening have not been exercised in this environment.

Human checklist (pending): configure a local demonstration instance; launch from stopped state; repeat Start without duplicate processes; confirm Status; verify a clear error for an occupied port or unavailable service; Stop and confirm only owned services stopped; inspect that existing records/volumes remain intact; open Publisher with all services stopped. Record OS, Node/Docker versions, database mode, date/timezone and pass/fail without secrets. Test on a nonproduction demonstration installation first. Human browser acceptance of Publisher/Founder Workspace remains a separate checkpoint.

Portable installation used for local demo verification

This checkout already has Neo4j/JDK under ignored .local/enterprise-runtime. It listens on HTTP 17474 and Bolt 17687. The local .local/enterprise/neo4j-test.json selects http://127.0.0.1:17474 and retains its existing password. This is machine-local setup, not a portable path assumed on OpenFor's machine. Do not replace credentials or extract a second database over existing data.

Codex can set JAVA_HOME to the selected existing JDK, NEO4J_HOME to the selected portable database, and run its bin/neo4j.ps1 console. Wait for authenticated readiness before running the live rehearsal. Start the console in a managed terminal session; stop only the console started for this task when requested. The general launcher treats this installation as external and does not own its lifecycle. Select external mode if using the general Workspace launcher. Reuse existing services instead of starting competing listeners.

On this machine the live command is:

node tools/rehearse-openfor.mjs --database-config .local/enterprise/neo4j-test.json --organization openfor_demo_private

The command leaves live revisions in the dedicated demo organization and closes its own temporary API. Existing access files are not rewritten. See ACCEPTANCE.md for the two successful live runs and restart durability evidence.

Second-machine setup lessons

Assisted fresh-checkout setup passed in the macOS lab with portable Neo4j/JDK, ten live demo checks and service-restart data preservation. See OPENFOR_DEMO.md for the environment and limits. Docker was not used. An unsupported fleet setting required a local configuration correction; its exact key was not supplied, so do not guess a replacement or disable configuration validation. Validate against the installed distribution and record the actual diagnostic/changed key.

During new-demo credential initialization, capture sensitive subprocess output privately and return redacted outcomes. Do not echo generated passwords or raw initialization commands/errors into chat. The lab replaced a generated password exposed by an initialization failure before successful initialization; this is a lesson to prevent recurrence, not a verified code fix to an installer (no installer is provided). Preserve existing initialized credentials. Elevated permission to bind loopback services may be required by the host sandbox; use only the necessary permission and never expose listeners publicly.
