Incubator graph reference implementation

Current interface: Research Workspace maintains authorized investor/startup data through Codex only. Browser administration routes are retired; backend APIs remain. Old browser-workbench descriptions below concern retained source compatibility, not the current interface. Research Publisher prepares reviewed recipient bundles separately; delivery is manual/explicit. See enterprise/OPERATOR.md for raw-data mapping and revision recovery.

Purpose and status

This optional reference adds a Neo4j Community database and a Node 24 backend alongside the existing Startup Tarot browser app. An incubator can import its own investor profiles, startup snapshots and sourced relationships. The same bounded graph-plan contract supports browser and database execution. The supplied alpha and beta datasets are entirely fictional; neither is an anonymized customer dataset.

The local reference milestone is implemented and exercised against Neo4j 2026.10.1, including an authenticated API demonstration. It is not a production service or independent security assessment. Real customer imports, identity-provider integration, live per-user OAuth/model acceptance and real-browser usability review remain adoption gates. See acceptance evidence.

Components and data flow

Incubator JSON bundle -> validate -> authenticated admin import
                                    |
                         Neo4j immutable scoped revision
                                    |
Browser or API client -> credential -> authorized organization/user
                                    |
             question + dated catalog + bounded graph plan
                                    |
            validate plan; filter eligible edges by dates/permissions
                                    |
            native Neo4j paths and investment projections
                                    |
               parity checks, shared network metrics
                       and evidence assembly
                                    |
          inspect packet -> model/manual response -> reference checks

Neo4j stores entity nodes and relationships as native graph records, plus exact import JSON for lossless reconstruction. IDs, sources, dates and criteria survive round trips. Imports write an immutable revision and move the active pointer in one database transaction. An expected-revision check prevents stale imports from overwriting newer work. Failed validation leaves the active data unchanged. Prior organization revisions remain available for reproducible research.

Path traversal and shared-round/shared-company pair discovery execute in Cypher. Date/permission filtering and network centrality use the shared JavaScript implementation. Results are checked against the existing browser semantics and fail explicitly on disagreement. This implementation retains the small reference limits; it is not a large-network performance benchmark.

The original browser-only Startup Tarot app remains usable without this backend or Neo4j. The reference has its own small web interface and API; it does not silently replace the published site's storage or model connection.

Local setup

For the recommended Codex-assisted data and release workflow, see Operator workflow. This document is the technical backend/API reference. For repeatable daily startup after one-time configuration, use the Local Services Launcher: double-click start-workspace.cmd or run node enterprise/launch.mjs start. It reuses healthy services, starts supported missing services, waits for readiness and opens the browser. Status/stop commands preserve unowned services and data. Docker mode can start the supplied Compose service; external/portable instances must already be running. The manual setup below remains the first-time provisioning path.

Requirements: Node 24 and either Docker Compose or an authenticated Neo4j Community 2026.10.1 instance. No global Node packages are required. Run commands from the repository or extracted reference-package root.

  1. Set a strong NEO4J_PASSWORD in your local process environment. Keep it outside the repository and chat. For Docker, start the database with the following command. The compose file binds database ports only to loopback, persists data in a named volume and disables vendor usage reporting and Fleet discovery.
docker compose -f enterprise/compose.yaml up -d
  1. Set NEO4J_URL to http://127.0.0.1:7474 (or your instance's URL). Remote connections require HTTPS. NEO4J_DATABASE defaults to neo4j for the server. The supplied demo-management and integration commands use the default neo4j database.
  1. Generate local reference credentials and import the fictional examples:
node enterprise/manage.mjs init
node enterprise/manage.mjs seed-demo

The init command refuses to overwrite existing files. It creates .local/enterprise/access.json containing token hashes and authorized organization/subject/role mappings. The separate demo-credentials.json contains the corresponding plaintext credentials for local testing. Both are ignored working files, excluded from all packages and never served over HTTP. File mode 0600 is requested; administrators must review Windows ACLs separately.

The seed-demo command updates only the example_alpha and example_beta workspaces. It creates a new revision rather than deleting prior imports. It does not initialize private contacts. Use the admin import API for your own separately provisioned organization.

  1. Start the backend:
node enterprise/server.mjs

Open http://127.0.0.1:8790. REFERENCE_PORT changes the port. REFERENCE_ACCESS_FILE can select a different ignored credentials configuration. The server binds only to 127.0.0.1 and serves allowlisted Workspace, browser-only Publisher and temporary preview assets. It does not expose Neo4j credentials, source files or local working directories.

For an existing installation, keep the same database password. Changing NEO4J_AUTH does not rotate an already initialized Neo4j account. Stop the reference with Ctrl+C; stop Docker with docker compose -f enterprise/compose.yaml stop. Do not remove the named volume unless you intend to erase its stored reference data.

End-to-end fictional demonstration

  1. Open demo-credentials.json locally and copy the example_alpha founder credential into the reference page. Choose Load authorized workspace. The credential stays in page memory; it is not stored in browser local storage.
  2. Inspect the imported investor/startup records. Select investor profiles and startup snapshots (at most five records total), review startup context and dates, then choose Prepare packet and catalog. The first profile and snapshot are selected initially; change or deselect them as needed.
  3. Choose Use scripted fictional plan. This loads a fixed demonstration plan; no LLM or external model request occurs.
  4. Choose Execute in Neo4j and prepare final prompt. Inspect the snapshot/activity path, source-edge references and star-network metrics. The center has degree three and normalized betweenness one in the included fictional network.
  5. Export the inspected prompt locally if desired. Sending it to another model is a separate decision. A manually supplied response can be checked against the expanded packet's evidence IDs. Reference checks do not prove semantic support.
  6. Forget the credential, then load the example_beta founder credential. The IDs overlap intentionally, but the returned names/data are beta's. A revision from alpha cannot be read through beta's credential.
  7. For an import demonstration, load the alpha administrator credential and select enterprise/fixtures/alpha.json in Administrator import. A researcher credential cannot import organization research.

Private-path examples are covered by the integration test and documented owner API. The page deliberately never merges private contact data into organization research or model prompts.

Provision an incubator workspace

For a local reference trial, reassign an unused generated administrator credential rather than copying a token-hash row. In the ignored access.json, change that entry's org and subject to the intended organization/user, retaining role admin. Update the matching descriptive labels in demo-credentials.json so you can identify its existing token. Organization and subject IDs must start with a lowercase letter and contain 3–64 lowercase letters, digits, underscores or hyphens. Token hashes must remain unique. Restart the backend after configuration changes; keep copies of the previous configuration outside public files.

Load that credential in the reference page. A new organization initially reports Dataset/revision not found; this is expected before its first import. The credential remains active, so select your complete bundle in Administrator import and import it. The page supplies expected_revision null for the first import and the loaded revision for later updates. Then load the workspace to inspect the data. Reassign another unused credential with the same org and role researcher for a second member, or provision additional unique credentials through your organization's identity integration. The reference does not provide an organization/signup administration interface.

Do not run seed-demo as a customer-data import tool: it only writes the two named fictional example workspaces. Keep customer bundles in an ignored imports directory or another private location.

Distribute to browser users

Administrators can export the loaded revision through the web page or POST /v1/distribution/export with an explicit revision. The operator distribution guide describes approval, modular manifests, browser preview/ZIP controls and the alternative CLI workflow. Private-owner graphs and server credentials are not selected. Downloaded copies remain independent and cannot be remotely revoked through this reference.

Import contract

{
  "schema_version": 1,
  "pack": { "schema_version": 2, "id": "your_pack", "provider": { "id": "your_provider" } },
  "relationships": {
    "schema_version": 1,
    "id": "your_relationships",
    "version": "1.0.0",
    "dataset_kind": "research",
    "pack_id": "your_pack",
    "provider_id": "your_provider",
    "nodes": [], "edges": [], "sources": []
  }
}

The pack above is abbreviated, not a valid complete import. Use the complete fictional fixture as a structural example and the existing Guide Pack v1/v2 contract for investor profiles, criteria, snapshots, licensing and rights-review metadata. The JavaScript validators are authoritative; unknown/missing graph endpoints, sources, duplicate IDs, incompatible dataset kinds and provider/pack mismatches fail import. Optional profile_id and snapshot_id graph-node links must reference existing pack records. Legacy research Guide Pack v1 uses provider_id legacy on its relationship artifact; Guide Pack v2 uses its declared provider ID. Use Guide Pack Kit for research authoring; this reference does not change Guide Pack v2.

Investor profiles preserve typed fit_claims and currencies; graph overlap cannot create or override eligibility criteria. Startup snapshots preserve their source-bound fields and dates. Nodes may represent investors, startups, rounds, snapshots, experiments and topics. Public/organization research graphs reject person nodes and knows edges. Graph sources carry id, title, url, published_date where known and checked_date. Edges carry id, from, to, type, basis, statement, source_ids, event_date/validity where known and limitations.

Same-round evidence uses investor -> participated_in -> round -> round_for -> startup. Mere invested_in membership supports shared-company analysis, not a shared round. Preserve unknown dates as unknown. Historical availability excludes unknown or later publication dates; a later retrospective article does not become contemporaneous evidence.

For Guide Pack v2, pack and relationship dataset_kind must agree: research or fictional. Legacy Guide Pack v1 is treated as research and requires a research relationship artifact. Fictional examples remain explicitly fictional in packets and cannot enter live model-adapter routes. Imports do not accept private contact datasets or authorization fields. The authenticated credential supplies the destination organization; a bundle cannot select another tenant.

Limits: 5 MiB import; existing pack record limits; 300 graph nodes, 1,000 edges and 1,000 sources; three plan queries, four research hops, five returned paths per research query, twenty selected relationship edges, sixty packet evidence items and 60,000 packet bytes. Private path queries retain the existing six-hop/thirty-path maximum. Exceeding evidence/packet limits fails without silently dropping evidence.

Validate an import without touching the database:

node enterprise/manage.mjs validate path/to/incubator-bundle.json

Authenticated API

All v1 routes use POST with Content-Type application/json and Authorization Bearer followed by the user's opaque credential. Organization, subject and role are resolved from server configuration, never trusted from request JSON. The server rejects attempted org/owner/role overrides and arbitrary Cypher. No CORS access is granted. Dataset/revision reads are scoped inside the database queries as well as the API boundary.

The plan shape is the existing GRAPH_PLAN_SCHEMA in js/graph-research.js: summary and up to three queries with kind, from, to, max_hops, projection and reason. Path queries use existing catalog IDs, max_hops 1–4 and projection null. Network queries use from/to null, max_hops 1 and projection same_round or shared_company. No strings are evaluated as code or interpolated as entity IDs into Cypher.

Private imports use the existing private relationship schema and explicit permission to store the records. Their owner is the authenticated subject, even for administrators. Edges require directional knows records, founder notes, checked dates, permission, confirmation and willingness. Expired, revoked or declined edges cannot support a confirmed path. A previous private revision cannot bypass current revocation: private path requests always use the current revision, and a stale supplied revision returns 409. Prior private records remain in the database for audit; deletion/retention policy is an adoption task, not implemented erasure.

Model connection boundary

The reference supports prompt export/manual response validation without model credentials. A reference workspace credential is still required for access. Its default scripted planner uses fictional data and never invokes an LLM. The standard server command provisions no shared model account.

For research data, an integrator may pass a modelAdapters Map to createReferenceServer, keyed by JSON.stringify([org, subject]). Each adapter has plan and reason functions. The service provides a bounded packet/catalog to planning and an expanded packet to reasoning; it validates the returned plan and output. Consent is required separately for each model request. No private owner graph is supplied to either function. The web page exposes the scripted/manual flow; live adapters are invoked through the authenticated API after an integrator provisions them. Research results are returned to the client, not saved as database run history; export an inspected prompt or retain API responses privately when an audit record is needed.

enterprise/model-adapter.mjs provides createOAuthModelAdapter for the existing OAuth Responses adapter. Supply a separately authenticated ResearchOAuth object per organization/user. Registration, callback routing, model discovery and user onboarding for a hosted multi-user deployment remain integration work; the reference does not borrow the developer's running helper connection or Codex credentials. Injected-model contract tests are not live OAuth acceptance.

Isolation and operations

Organization and private-owner scope keys are derived on the server. Every stored node, edge, revision and workspace carries scope and organization identifiers. Native queries constrain all traversed nodes and edges to one scope/revision. The app uses a database service account, so isolation is an application policy, not independent Neo4j row-level security or physical database separation. The database administrator can access the underlying store.

The supplied backend stays local. Remote use needs a deliberate deployment design: HTTPS/reverse-proxy host handling, an identity provider and membership lifecycle, expiring/revocable sessions, least-privilege database accounts, rate limits, operational monitoring, encrypted backups, tested restore, retention/deletion rules and independent security review. The static bearer configuration is a local reference mechanism, not enterprise SSO. Rotating/removing a reference credential requires updating the local configuration and restarting the backend.

Database files persist in the named Docker volume or configured portable instance directory. Back up both the graph database and protected access configuration before upgrades. Follow the official offline dump/load guidance for Community; backup/restore exercises and load testing are not claimed as completed. Keep imports, exports, credentials and raw customer data outside public repositories. Export packages use an explicit file allowlist and exclude .local, access credentials and database volumes.

Verification and packaging

From a repository checkout, run the application/reference unit and API checks:

node --test tests/enterprise.test.mjs

From either the checkout or the standalone reference package, run:

node --test enterprise/tests/contracts.test.mjs
node --test enterprise/tests/neo4j.integration.mjs
node enterprise/export-reference.mjs

The checkout-only tests/enterprise.test.mjs file is intentionally excluded from the standalone package because it also uses the main app's public research fixtures.

The integration test requires NEO4J_URL and NEO4J_PASSWORD. Without a password/config, it reports skipped, not passed database acceptance. An ignored REFERENCE_INTEGRATION_CONFIG JSON file containing url/password can supply local test configuration instead. Tests create unique fictional namespaces and retain them for audit; use a disposable reference database or volume. They never reset customer workspaces.

The separate package under release/incubator-reference-* contains code, fictional alpha/beta data, this guide, tests and a SHA-256 file manifest. It includes a fictional default browser template and the selected OpenFor public-source sample plus illustrative companion. It excludes raw bulk datasets, private runtime files, credentials and database volumes. The normal browser release remains a separate artifact.
